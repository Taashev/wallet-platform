# PRD: Users Service Web MVP

Дата: 2026-04-19
Статус: Draft v1
Расположение: `frontend/docs`

## 1. Обзор приложения и цели

Цель первой MVP-версии: реализовать клиентское веб-приложение на `React + TypeScript`, которое работает строго поверх текущей реализации `users-service` и покрывает только уже существующие backend-возможности.

Приложение не должно моделировать будущие возможности `Wallet Platform`, если они не подтверждены текущим API. Развитие клиента планируется параллельно с развитием backend, поэтому текущий MVP должен быть компактным, устойчивым и легко расширяемым.

Основная задача MVP:

- предоставить пользователю входную точку в систему;
- дать возможность зарегистрироваться, войти и поддерживать сессию;
- позволить просматривать и редактировать собственный профиль;
- позволить менять пароль и завершать сессию;
- предоставить каталог пользователей с поиском по `username` и пагинацией;
- корректно обрабатывать ограничения и ошибки текущего API.

## 2. Целевая аудитория

Основная аудитория MVP:

- конечный пользователь платформы, которому нужен личный кабинет;
- пользователь, которому нужно зарегистрироваться и поддерживать собственный профиль в актуальном состоянии;
- авторизованный пользователь, которому нужен список других пользователей в системе.

На этой стадии не рассматриваются отдельные роли администратора, модератора или оператора. Все сценарии строятся вокруг обычного авторизованного пользователя.

## 3. Продуктовые границы MVP

### Что входит в MVP

- регистрация нового пользователя;
- вход по `username` и `password`;
- обновление access/refresh токенов;
- выход из текущей сессии;
- просмотр собственного профиля;
- редактирование собственного профиля;
- смена пароля;
- мягкое удаление собственного аккаунта;
- просмотр списка пользователей;
- поиск пользователей по `username`;
- пагинация списка пользователей;
- базовые состояния интерфейса: `loading`, `empty`, `error`, `success`.

### Что не входит в MVP

- балансы;
- переводы;
- уведомления;
- realtime-функциональность;
- загрузка аватаров;
- чужой публичный профиль;
- восстановление пароля;
- подтверждение email;
- управление несколькими сессиями;
- роли и разграничение прав;
- оффлайн-режим;
- mobile app.

Все перечисленные возможности считаются будущими расширениями и не должны попадать в scope первой версии, пока не появятся в backend-контракте.

## 4. Подтвержденные backend-возможности

На основании текущего Swagger подтверждены следующие API:

- `POST /v1/auth/signup`
- `POST /v1/auth/signin`
- `POST /v1/auth/refresh`
- `POST /v1/auth/signout`
- `GET /v1/users/me`
- `PATCH /v1/users/me`
- `PATCH /v1/users/me/password`
- `DELETE /v1/users/me`
- `POST /v1/users?offset=&limit=&username=`

Подтвержденные поля пользователя:

- `userId: string`
- `username: string`
- `email: string`
- `about: string`
- `dateOfBirth: string`
- `age: number`

Подтвержденные токены:

- `accessToken: string`
- `refreshToken: string`

## 5. Основные пользовательские сценарии

### 5.1 Регистрация

Пользователь открывает страницу регистрации, вводит обязательные поля и создаёт аккаунт.

Ожидаемый результат:

- backend создаёт пользователя;
- клиент получает `accessToken` и `refreshToken`;
- пользователь переводится в авторизованное состояние;
- после успешной регистрации пользователь попадает в личный кабинет.

Acceptance criteria:

- форма регистрации содержит поля `username`, `email`, `password`;
- поля `about` и `dateOfBirth` могут быть опциональными в UI, если это не противоречит текущему контракту;
- при `409` интерфейс показывает понятную ошибку уникальности;
- после успешной регистрации токены сохраняются и используются в следующих запросах.

### 5.2 Вход

Пользователь авторизуется по `username` и `password`.

Acceptance criteria:

- форма входа содержит `username` и `password`;
- при `401` пользователь получает понятное сообщение об ошибке;
- после успешного входа пользователь попадает на защищённый экран;
- токены сохраняются и используются для защищённых запросов.

### 5.3 Восстановление сессии

Клиент должен поддерживать пользовательскую сессию без повторного логина, пока backend считает refresh token валидным.

Acceptance criteria:

- при истечении `accessToken` клиент пытается выполнить `refresh`;
- после успешного `refresh` исходный запрос повторяется автоматически;
- при неуспешном `refresh` пользователь переводится в неавторизованное состояние;
- UI не зависает в бесконечной попытке обновления токена.

### 5.4 Просмотр и редактирование профиля

Пользователь просматривает текущие данные и при необходимости обновляет `username`, `email`, `about`, `dateOfBirth`.

Acceptance criteria:

- экран профиля отображает актуальные данные из `GET /v1/users/me`;
- экран редактирования поддерживает только поля, разрешённые `PATCH /v1/users/me`;
- после успешного обновления данные профиля синхронно обновляются в UI;
- ошибки валидации и ошибки сохранения отображаются рядом с формой.

### 5.5 Смена пароля

Пользователь может изменить пароль, указав старый и новый.

Acceptance criteria:

- форма содержит `oldPassword` и `newPassword`;
- при успешной операции пользователь получает явное подтверждение;
- при ошибке старого пароля или валидации интерфейс показывает корректное сообщение;
- в PRD не предполагается автоматический logout после смены пароля, если backend это явно не гарантирует.

### 5.6 Выход из системы

Пользователь завершает текущую сессию.

Acceptance criteria:

- по нажатию `Sign out` вызывается `POST /v1/auth/signout`;
- локальные токены очищаются;
- пользователь переводится на публичный экран;
- защищённые маршруты перестают быть доступными без повторной авторизации.

### 5.7 Удаление аккаунта

Пользователь может выполнить мягкое удаление собственного аккаунта.

Acceptance criteria:

- удаление подтверждается отдельным модальным окном или confirm-экраном;
- при успешном ответе `204` пользователь разлогинивается локально;
- удаление нельзя вызвать случайно из основного экрана без подтверждения.

### 5.8 Список пользователей

Авторизованный пользователь может просматривать каталог пользователей.

Acceptance criteria:

- список загружается только для авторизованного пользователя;
- поддерживаются `offset`, `limit`, `username`;
- пользователь видит состояния загрузки, пустого списка и ошибки;
- в первой версии нет перехода на детальную страницу другого пользователя, так как это не подтверждено API;
- UI должен поддерживать серверную пагинацию.

## 6. Информационная архитектура и экраны

Минимальный набор экранов:

- `Sign In`
- `Sign Up`
- `Profile`
- `Edit Profile`
- `Change Password`
- `Users List`
- `Delete Account Confirmation`

Роутинг MVP:

- публичные маршруты:
  - `/sign-in`
  - `/sign-up`
- защищённые маршруты:
  - `/profile`
  - `/profile/edit`
  - `/profile/password`
  - `/users`
  - `/profile/delete`

Правила навигации:

- неавторизованный пользователь при попытке открыть защищённый маршрут переводится на `/sign-in`;
- авторизованный пользователь при открытии `/sign-in` или `/sign-up` может быть автоматически перенаправлен на `/profile`;
- верхний уровень интерфейса должен содержать понятную глобальную навигацию между `Profile`, `Users`, `Sign out`.

## 7. UI/UX принципы

Принципы первой версии:

- интерфейс должен быть простым и утилитарным;
- все формы должны иметь явные состояния валидации;
- ошибки API не должны теряться или отображаться только в console;
- пользователь всегда должен понимать, авторизован он или нет;
- потенциально опасные действия должны требовать подтверждения;
- интерфейс должен быть адаптивным для desktop и mobile web;
- ключевые действия должны быть доступны без сложной навигации.

Особенности UX:

- `Users List` должен иметь поиск по `username` и сброс фильтра;
- `Profile` должен отображать read-only версию данных и явную кнопку редактирования;
- после каждой успешной мутации должен быть видим короткий success feedback;
- при недоступности backend должен отображаться recoverable error state с возможностью повторить запрос.

## 9. Функциональные требования

### Аутентификация

- приложение должно поддерживать публичную и защищённую зоны;
- клиент должен хранить auth-state и уметь восстанавливать сессию;
- клиент должен использовать `Bearer access token` для защищённых запросов;
- клиент должен уметь обновлять токены через `refresh`.

### Профиль

- приложение должно получать и отображать текущего пользователя;
- приложение должно поддерживать обновление допустимых полей профиля;
- приложение должно показывать ошибку, если профиль не найден или токен недействителен.

### Пароль

- приложение должно поддерживать смену пароля текущего пользователя;
- форма смены пароля должна иметь минимальную локальную валидацию.

### Список пользователей

- приложение должно загружать пользователей с серверной пагинацией;
- приложение должно поддерживать фильтрацию по `username`;
- приложение не должно обещать пользователю те сценарии, которые не покрыты API.

## 10. Нефункциональные требования

- стек реализации: `React + TypeScript`;
- приложение должно быть подготовлено к дальнейшему росту без крупного переписывания;
- архитектура должна быть пригодна для параллельного расширения по мере появления новых backend-модулей;
- код должен быть модульным и предсказуемым;
- основные пользовательские действия должны выполняться в разумное время при нормальной доступности backend;
- UI должен корректно работать в актуальных desktop и mobile браузерах;
- ошибки сети и API должны обрабатываться централизованно;
- приложение должно поддерживать конфигурацию окружения через переменные окружения frontend.

## 11. Рекомендации по техническому стеку

Обязательная база:

- `React`
- `TypeScript`

Рекомендуемый концептуальный стек:

- `React Router` для маршрутизации;
- `TanStack Query` для server-state и кэширования;
- HTTP-клиент уровня `fetch wrapper` или `axios` с единым API-слоем;
- схема валидации форм через `zod` или аналогичный инструмент;
- form library уровня `react-hook-form` для управляемых форм;
- централизованная конфигурация `API base URL` через env.

Рекомендация:

- для MVP выбрать SPA-архитектуру с route-first структурой и явным разделением на `app`, `pages`, `features`, `shared`;
- не использовать тяжёлое глобальное state-решение вроде Redux, пока бизнес-объём ограничен auth/profile/users;
- проектировать API-слой так, чтобы позже можно было добавить новые домены без перестройки основы.

## 12. Рекомендуемая frontend-архитектура

### Архитектурный подход

MVP должен быть реализован как модульный SPA-клиент с акцентом на:

- защищённый роутинг;
- централизованную работу с API;
- предсказуемую работу с auth-сессией;
- раздельные feature-модули.

### Предлагаемая структура

- `app`
  - bootstrap приложения
  - router
  - auth guard
  - layout
  - providers
- `pages`
  - route-level страницы
- `features/auth`
  - sign-in
  - sign-up
  - sign-out
  - refresh-session
- `features/profile`
  - get profile
  - edit profile
  - change password
  - delete account
- `features/users`
  - users list
  - search
  - pagination
- `shared/api`
  - http client
  - interceptors
  - dto mappings
  - error normalization
- `shared/ui`
  - form primitives
  - buttons
  - input components

### Причины выбора

- объём MVP небольшой и не требует сложной глобальной модели состояния;

- `TanStack Query` подходит для чтения и мутаций поверх API-контракта;
- auth-flow изолируется в одном месте и не размазывается по приложению.

## 13. Безопасность

Первая версия должна учитывать следующие правила:

- все защищённые запросы выполняются только с валидным `accessToken`;
- при `401` клиент должен корректно обрабатывать истечение сессии;
- refresh-механизм должен быть централизованным и не создавать гонки запросов;
- чувствительные действия должны быть защищены UI-подтверждением;
- клиент не должен логировать токены в открытом виде;
- в интерфейсе не должно быть предположений о ролях или правах, которых нет в контракте.

Открытый архитектурный риск:

- текущий API передаёт `refreshToken` в body, а не через `httpOnly cookie`;
- для веб-клиента это означает повышенные требования к безопасному хранению токена на стороне frontend;
- в рамках MVP допускается зафиксировать это как текущее ограничение backend и не менять контракт на уровне PRD.

## 14. Ограничения и зависимости

Ограничения текущего backend:

- отсутствует API чужого профиля;
- отсутствует API балансов, переводов и уведомлений;
- отсутствует API аватаров;
- отсутствуют формализованные схемы ошибок;
- `POST /v1/users` используется как операция чтения;
- нет backend-контракта на forgot password и email verification.

Критические зависимости:

- доступность `users-service`;
- корректный `API base URL`;
- CORS-конфигурация backend для frontend-окружений;
- стабильность формата ошибок backend;
- определённая стратегия хранения токенов на клиенте.

## 15. Потенциальные проблемы и способы их решения

### Неоднозначность полей профиля

Проблема:

- часть полей профиля обязательна в ответе, но не обязательна в запросах.

Подход:

- заложить tolerant rendering в UI;
- зафиксировать в frontend-контрактах безопасную обработку пустых значений;
- при появлении formal backend-rules синхронизировать формы.

### Неполная схема ошибок

Проблема:

- трудно строить точные пользовательские сообщения без стабильного error model.

Подход:

- централизовать нормализацию ошибок;
- для MVP покрыть базовые случаи `400`, `401`, `404`, `409`;
- не завязывать UI на нестабильный текст backend.

### Хранение refresh token

Проблема:

- контракт не ориентирован на web-best-practice с `httpOnly cookie`.

Подход:

- в MVP зафиксировать выбранную стратегию хранения как техническое ограничение;
- изолировать работу с токенами в одном модуле, чтобы позже можно было заменить механизм.

### Рост backend-контракта

Проблема:

- frontend будет развиваться параллельно с backend, значит API будет расширяться.

Подход:

- строить frontend по доменам;
- не смешивать временные решения с общим app-layer;
- выделить устойчивые feature boundaries уже в MVP.

## 17. Критерии приемки MVP целиком

MVP считается готовым, если:

- пользователь может зарегистрироваться и войти через UI;
- защищённые маршруты недоступны без авторизации;
- профиль текущего пользователя отображается корректно;
- данные профиля можно изменить через UI;
- пароль можно изменить через UI;
- пользователь может завершить сессию;
- пользователь может инициировать мягкое удаление аккаунта;
- список пользователей открывается после авторизации;
- поиск по `username` и пагинация работают;
- базовые ошибки API и сети не ломают приложение;
- архитектура позволяет безболезненно добавлять новые backend-домены позже.

Следующие направления сознательно исключены из MVP, но должны учитываться как будущие расширения архитектуры:

- баланс и операции кошелька;
- переводы между пользователями;
- realtime-уведомления;
- лента уведомлений;
- управление файлами и аватарами;
- публичные профили;
- роли и админские сценарии;
- управление сессиями и устройствами;
- полноценная дизайн-система и расширенный кабинет.

## 19. Резюме решения

Первая версия продукта должна быть реализована как компактный веб-кабинет над текущим `users-service`, а не как frontend для всей концепции `Wallet Platform`. Это снижает риск ложных ожиданий, ускоряет разработку и создаёт устойчивую основу для параллельного роста клиента и backend.
